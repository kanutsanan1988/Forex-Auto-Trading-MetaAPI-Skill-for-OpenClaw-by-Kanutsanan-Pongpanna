## 1) หลักการทำงานที่เจ้าของระบบกำหนด (ใช้เป็นกติกาถาวร)

1. **ข้อมูลจริงเท่านั้น** — ห้ามสมมติ/เดา ตัวเลขทุกตัวต้องมาจาก audit, ราคา M1/M5 จริง หรือผลจำลองที่รันซ้ำได้
2. **ประเมินก่อนแก้เสมอ** — ทุกข้อเสนอต้องมีตัวเลขรองรับ และรายงาน "ตัวที่ไม่ผ่านเกณฑ์" แยกจาก "ตัวที่ผ่าน"
3. **รายงานสั้น อ่านปั๊บเข้าใจ** — ตัวที่ไม่ผ่านบอกแค่ชื่อ ตัวที่ผ่านแสดงตัวเลข
4. **แยกชั้น LLM ออกจากเทรดคอร์** — เทรดคอร์ต้องทำงานได้แม้ไม่มี LLM
5. **ระบบต้องใช้งานง่ายสำหรับคน** — ปุ่ม `.cmd` ทุกงาน · คู่มือ · ระบบตรวจสุขภาพ
6. **มีค่าโรงงานสำรอง** — คืนค่าได้ทุกเมื่อ (เหมือนรีเซ็ตโทรศัพท์กลับค่าตั้งต้น)
7. **โครงสร้างโค้ด = สิทธิ์มนุษย์** — บอทปรับได้เฉพาะ "ค่าต่างๆ" และ "โครงสร้างสกิล" ในกรอบ
8. **เจ้าของระบบสั่งเปิด/ปิดระบบเทรดเอง** — ห้ามสตาร์ท/หยุดเทรดเดอร์หรือลบ kill switch เองโดยไม่ได้รับอนุมัติ

## 2) บทเรียนสำคัญ (จากของจริงวันนี้)

### 2.1 "ตัวปรับที่ขยันเกินไป" ทำให้ระบบตัน
ตัวปรับคำนวณ band ใหม่ทุก 1–3 นาที → band แคบลงเหลือ 0.02 → ไม่มีสัญญาณผ่านเลย
**แก้ที่ต้นเหตุ:** ตั้ง **ความกว้างขั้นต่ำมาตรฐาน** (0.10 ทุกมิติ) แล้วบังคับเป็นขั้นสุดท้ายของตัวปรับ + churn guard
> **บทเรียน:** กลไกที่ "ปรับตัวเองได้" ต้องมี "พื้นขั้นต่ำ" เสมอ ไม่งั้นมันจะเรียนรู้จนปิดตัวเอง

### 2.2 ตัวชี้วัดที่ดูดี ≠ กำไรจริง
ระบบมี win rate ~64% แต่ **ขาดทุนสุทธิ** เพราะไม้ชนะเล็กกว่าไม้แพ้ (ปิดกำไรที่ 1/10 ของ TP)
**แก้:** ปิดกำไรที่ **0.8 ของ TP** → ผลทดสอบจริงดีขึ้นจาก −0.50R เป็น **+5.80R**
> **บทเรียน:** วัดที่ **net** เสมอ ไม่ใช่อัตราชนะ · และตรวจ "ขนาดไม้ชนะเทียบไม้แพ้" เป็นประจำ

### 2.3 ทฤษฎีตลาดต้องผ่านการทดสอบด้วยราคาจริง
เจ้าของระบบเสนอ "ไม้สวนแนวโน้มควร TP สั้นกว่า SL" (ฟังดูสมเหตุสมผล) แต่ข้อมูลจริง 107–116 ไม้ชี้ว่า **แย่ลงทุกระดับ**
**มติ:** ใช้ "ยกพื้นคัดกรอง +0.05" แทน — และจำกัดการยกไม่เกิน 80% ของความกว้าง band เพื่อไม่ให้ประตูตัน
> **บทเรียน:** เสนอทฤษฎีได้เสรี แต่ต้องจำลองก่อนใช้เงินจริง และต้องมี "เพดานกันตัน" ทุกครั้งที่ยกเกณฑ์

### 2.4 กลไกเดียวกันใช้กับทุกกรณีไม่ได้
"ตัดเมื่อสัญญาณสวนทาง" ให้ผล **+$2.39 กับไม้ที่ขาดทุน** แต่ **−$1.93 กับไม้ที่กำไร**
**แก้:** แยกเป็น 2 ทาง — ไม้ขาดทุน → ตัดทันที (`early_cut`) · ไม้กำไร → ปิดกำไรตามกติกาเดิม
> **บทเรียน:** ก่อนใช้กลไกใหม่ ต้องแยกกลุ่มทดสอบ (ชนะ/แพ้) แล้ววัดแยกกัน

### 2.5 เครื่องมือของบอทเองก็มีบั๊กได้
วันนี้เจอบั๊ก 3 จุดที่ตัวบอทสร้างเอง: ตัวแปรไม่มีนิยาม (`rejected`), คีย์ซ้ำใน dict, และสคริปต์ตรวจสุขภาพเรียก `datetime` ที่ถูกลบไปแล้ว
> **บทเรียน:** รัน `pyflakes` + compile กับโค้ดที่รันจริงเป็นประจำ · และ**ทดสอบเครื่องมือที่เพิ่งเขียน**ทันที (สคริปต์ตรวจสุขภาพเองก็ต้องถูกตรวจ)

### 2.6 การรีสตาร์ทบน Windows มีกับดัก
สคริปต์รีสตาร์ทของระบบใช้ PowerShell `Start-Process` แล้วล้มด้วย error **-1073741502** (บางจังหวะ) และพาซุปเปอร์ไวเซอร์ดับไปด้วย
**วิธีที่ได้ผล:** รันซุปเปอร์ไวเซอร์เป็น **โปรเซสพื้นหลังของ Hermes** (ไม่เปิดหน้าต่าง) · ถ้าต้องรีสตาร์ทตัวเทรด ให้หยุดเฉพาะโปรเซสตัวเทรด — ซุปเปอร์ไวเซเซอร์จะสตาร์ทใหม่ให้เองใน 10 วินาที
> **บทเรียน:** อย่าใช้สคริปต์รีสตาร์ทที่ "ฆ่าทั้งซุปเปอร์ไวเซอร์" ในเวลาที่ตลาดเปิด — ให้ฆ่าเฉพาะตัวเทรด

### 2.7 "บอทดูแล LLM" ดีกว่า "สคริปต์ต่อ LLM ตรง"
การให้บอท (Hermes/Codex/Cursor ฯลฯ) เป็นผู้ใช้ LLM ทำให้ได้บริบทมากขึ้น: บอทอ่านผลวิจัยภายใน + ข้อมูลของตัวเอง + วงจรคำแนะนำเดิม แล้วคิดต่อ
**และเพิ่มประตูโหมด:** โหมด 1 (ข้อมูลภายใน) ไม่เรียก LLM เลย → ประหยัดเครดิต 100%
> **บทเรียน:** วาง LLM ไว้ "หลังบอท" ไม่ใช่ "ในสคริปต์" — และให้สคริปต์เตรียมข้อมูล (ไม่คิด) เพื่อให้ทดสอบ/ตรวจสอบได้

### 2.8 สคริปต์เปิดระบบล้ม แต่ระบบไม่ได้พัง — ผิดที่ "วิธี spawn โปรเซส"
`Start-Process -WindowStyle Hidden` บนเครื่องนี้ล้มด้วย exit **-1073741502** (0xC0000142 = DLL init failed) ทำให้ปุ่มเปิดระบบใช้ไม่ได้เป็นเดือน โดยที่ตัวเทรดเองไม่มีปัญหาเลย
**แก้:** ให้สคริปต์ลองหลายวิธีเรียงลำดับ (Task Scheduler → Start-Process → WMI) และ **ตัดสินความสำเร็จจากไฟล์ PID ที่ซูเปอร์ไวเซอร์เขียนเอง** ไม่ใช่ exit code ของตัวเรียก
> **บทเรียน:** (1) อย่าตัดสินว่า "สำเร็จ" จาก exit code ของตัวสั่ง — ให้ดูที่หลักฐานที่ปลายทางสร้าง (ไฟล์ PID/lock/audit)
> (2) เมื่อกลไกหนึ่งใช้ไม่ได้บนเครื่องหนึ่ง ให้เลียนแบบวิธีที่ "พิสูจน์แล้วว่าได้ผลบนเครื่องนั้น" (ที่นี่คือ Task Scheduler ซึ่ง Hermes gateway ก็ใช้)
> (3) ระวังกับดัก: `schtasks.exe` ตัดอาร์กิวเมนต์ผิดเมื่อ path มีช่องว่าง/อักษรไทย → ใช้ cmdlet `Register-ScheduledTask` แทน

### 2.9 ไฟล์ .ps1 ต้องมี BOM ถ้ามีข้อความไทยในสตริง
PowerShell 5.1 อ่านไฟล์ `.ps1` ที่ไม่มี BOM เป็น ANSI → ข้อความไทยใน **สตริง** เพี้ยนจน parse ไม่ผ่าน (ถ้าอยู่ในคอมเมนต์เท่านั้นจะรอด)
**แก้:** เขียนไฟล์ `.ps1` เป็น UTF-8 **มี BOM** เสมอ + ตรวจด้วย `Parser::ParseFile` ทุกครั้งหลังแก้
> **บทเรียน:** ทุกภาษา/ทุกเครื่องมือมี "กติกา encoding" ของตัวเอง — ตรวจด้วย parser จริง ไม่ใช่ดูด้วยตา

### 2.10 รายชื่อที่ฝังในโค้ด ต้องตรงกับความจริงเสมอ
`choose_mode.py` มีรายชื่องาน cron ฝังอยู่ (`JOBS = ('trading-research', ...)`) ซึ่งเป็นชื่อเก่าที่ถูกเปลี่ยนไปแล้ว และมีแค่ 3 จาก 5 งาน → ปุ่มปิดระบบ "ปิดไม่ครบ" โดยไม่มีใครรู้ (สคริปต์รายงานว่าสำเร็จบางส่วน)
**แก้:** อัปเดตชื่อจริงทั้ง 5 งาน + เพิ่มงานที่ตกหล่น
> **บทเรียน:** รายการ/ค่าคงที่ที่อ้างถึง "สิ่งที่อยู่ข้างนอกโค้ด" (ชื่องาน, path, คีย์ config) ต้องมีที่ตรวจว่าตรงกัน (เช่น `tools/health_check.py`) ไม่งั้นมันจะค้างเป็นชื่อผีและพังเงียบ ๆ

### 2.11 "ระบบที่ดูเหมือนทำงาน" อาจตาบอดอยู่ทั้งวัน ⭐
ตัวปรับประตู 36 ค่า อ่าน "180 records ล่าสุด" ดิบ ๆ — แต่ในช่วงที่ audit มีแต่เหตุการณ์ noise (เช่น `recommendation_retest_skipped`) หน้าต่างนั้นให้**ตัวอย่าง 0 ต่อคีย์** → ตัวปรับแทบไม่เคยทำงานเลย โดยที่ไม่มีใครรู้
**แก้:** เลือกเฉพาะ records ที่มีข้อมูลที่ตัวปรับใช้จริง → ตัวอย่างพุ่งเป็น **109.5/คีย์ · 7/12 คีย์ผ่านเกณฑ์**
> **บทเรียน:** ก่อนเชื่อว่า "กลไกอัตโนมัติทำงานอยู่" ต้องวัดว่า **มันมีข้อมูลป้อนเข้าจริงหรือไม่** (ไม่ใช่ดูแค่ว่าโค้ดถูกเรียก)

### 2.12 เครื่องมือตรวจสอบเองก็โกหกได้ (false positive)
ตัวตรวจอัตโนมัติรายงาน "ไม่ผ่าน" 3 ข้อ — แต่พอตรวจซ้ำโดยตัดคอมเมนต์/docstring ออก พบว่าเป็น **false positive ทั้ง 3** (ไปเจอข้อความอธิบาย ไม่ใช่โค้ดจริง)
**แก้:** ใช้ `ast` แยก "โค้ดจริง" ออกจาก "ข้อความ" ก่อนสรุป
> **บทเรียน:** ผลจากเครื่องมือตรวจต้องผ่านการยืนยันซ้ำด้วยวิธีที่ต่างออกไป — โดยเฉพาะก่อนรายงานว่า "มีปัญหา"

### 2.13 เทสต์ต้องไม่แตะข้อมูลจริง
เทสต์ตัวหนึ่งเรียกฟังก์ชันของเทรดคอร์ ซึ่งเขียน event ลง **audit ของจริง** → ข้อมูลที่ใช้วิเคราะห์/ปรับค่าถูกปนเปื้อนด้วยเหตุการณ์จากเทสต์ (เจอเพราะสงสัยว่า "ทำไม audit มี event หลังปิดระบบ")
**แก้:** ปิดการเขียน audit ในเทสต์ · ยืนยันว่ารันเทสต์แล้ว audit ไม่เพิ่มแม้แต่บรรทัดเดียว
> **บทเรียน:** เทสต์ที่ "อ่าน/เขียนข้อมูลจริง" คือความเสี่ยงเงียบ — ให้ใช้ temp/ไฟล์จำลอง หรือปิด side effect

### 2.14 ค่าโรงงานต้องบันทึก "เจตนา" ไม่ใช่ "สถานะชั่วคราว"
ปักหมุดโรงงานตอนระบบปิด → snapshot บันทึกทุกงานเป็น `enabled=false` → ถ้าคืนค่าโรงงานในอนาคต งานวิจัยจะไม่กลับมา
**แก้:** กำหนด `FACTORY_JOB_STATE` ให้โรงงานบันทึกสถานะที่ตั้งใจของงาน + ใส่ `factory_note` กำกับ
> **บทเรียน:** snapshot ของ "เป้าหมาย" ต้องไม่ขึ้นกับสภาพชั่วคราว ณ เวลาที่บันทึก

## บทเรียนเพิ่มเติม 2.15–2.20 (รอบ agentic AI + ระบบคำสั่ง)

### 2.15 "บอทเขียนได้" ≠ "สคริปต์ดึงไปใช้ได้"
ไฟล์คำแนะนำที่บอทเขียนไว้ (11:51 · 12:16) **ไม่ผ่าน `validate()`** เพราะ `auto_apply != true`
→ คำแนะนำตกหล่นเงียบ ๆ โดยไม่มีใครรู้ **บทเรียน:** ต้องมีระบบให้บอท **ตรวจของตัวเองก่อนส่ง** เสมอ
(สร้าง `submit_recommendation.py --check` + `CONTRACT.md` ที่สร้างจากโค้ดจริง)

### 2.16 เครื่องมือตรวจสอบเองก็ให้ "ผลลวง" ได้ — และถ้าเชื่อมันจะพังจริง

**บทเรียน:** ก่อนลบอะไรตามผลของเครื่องมือ ต้องดูบริบทจริง (global assignment ถูกใช้ข้ามฟังก์ชัน)

### 2.17 ตรรกะเดียวกันต้องอยู่ที่เดียว — ไม่งั้นเพี้ยนกัน
