# 2026-09-13 — "โหมดการเทรด" 2 โหมด: สัญญาณภายในเท่านั้น vs ร่วมสัญญาณ AI (LLM)

## 1. หลักการ: ทำไมแยกเป็น "โหมด" ไม่ใช่ "สวิตช์ใน config"

1. **ผู้ใช้เป็นเจ้าของการตัดสินใจ** — การให้ AI ร่วมตัดสินใจเป็นเรื่องเชิงนโยบาย ไม่ใช่พารามิเตอร์เทคนิค จึงเก็บเป็น "โหมด" ที่ผู้ใช้เลือกได้เอง (ไม่ให้ตัวปรับอัตโนมัติแตะ)
2. **แยกความรับผิดชอบชัดเจน** — โหมดคุม *ว่าสัญญาณใดมีสิทธิ์ออกเสียง* ส่วนตัวปรับ 36 ค่า/TP-SL คุม *ความยืดหยุ่น* ทั้งสองโหมดยังได้การปรับอัตโนมัติเต็มรูปแบบ
3. **ไม่ผูกกับ config เทรด** — ค่าโหมดเก็บที่ `work/trading_mode.json` (นอก `auto_config.json`) เพราะ validator ของ config จำกัดคีย์ที่อนุญาต และเพื่อให้เปลี่ยนโหมดได้โดยไม่ต้องรีสตาร์ทเทรดเดอร์

## 2. กลไกจริง (จุดเดียวที่โหมดมีผลต่อการตัดสินใจ)

```
รอบ 10 นาที (cron)
  โหมด 2: trading-research        → script research_analytics.py + [LLM] ตอบ [TRADE-SIGNAL]
  โหมด 1: trading-analytics       → script research_analytics.py เท่านั้น (ไม่เรียก LLM)
                                     ( trabajo ภายในพิมพ์ [INTERNAL-SIGNAL] เสมอทั้งสองโหมด )

รอบ 5 นาที (cron: llm-recommendation-consumer → llm_rec_consumer_runner.py)
  llm_signal_parser.py
    ├─ อ่าน output ของรอบ 10 นาที → parse [TRADE-SIGNAL] (LLM) + [INTERNAL-SIGNAL] (ภายใน)
    ├─ ★ trading_mode():
    │     internal_llm_join → avg = (คะแนน LLM + คะแนนภายใน) / 2      ← น้ำหนักเท่ากัน
    │     internal_only    → avg = คะแนนภายใน เท่านั้น (ทิ้งเสียง LLM แม้มี)
    └─ เขียน REC action `set_directional_weights` (12 ค่า, clamp 0.90–1.10) → consumer → TESTING GATE → apply → hot reload
```

**คะแนนเสียง** = `±(WEIGHT − 50)` โดย `WEIGHT` = 0–100 จากบล็อกของแต่ละเสียง · ทิศทาง `NEUTRAL` = 0
**ทางออกของโหมด 1:** ถ้าบล็อกภายในหาย → ไม่มีเสียง → ไม่เขียน REC (ระบบไม่เดาแทน)

## 5. Pitfalls (เจอจริง/ต้องระวัง)

1. **โหมดมีผลที่จุดเดียวคือ `merge_signals`** — ถ้าเพิ่มเส้นทางใหม่ที่นำสัญญาณไปใช้ (เช่น แจ้งเตือน Telegram ที่บอกทิศทาง) ต้องเช็คโหมดที่นั่นด้วย ไม่งั้นโหมด 1 จะยัง "เห็น" LLM อยู่
2. **อย่าเก็บโหมดไว้ใน `auto_config.json`** — validator จำกัดคีย์ + REC จะเขียนทับได้ → โหมดอาจถูกเปลี่ยนโดยไม่ตั้งใจ (ผิดเจตนาของผู้ใช้)
3. **โหมด 1 ไม่ได้ปิดงานวิจัย** — band_plan/tpsl_plan ยังรัน (ผ่าน `trading-analytics`) เพราะเป็น "การปรับโครงสร้างจากข้อมูลจริง" ไม่ใช่สัญญาณ LLM
4. **ค่าเริ่มต้น = โหมด 2** เพื่อความเข้ากันได้กับระบบเดิม; ถ้าไม่พบไฟล์โหมด ให้ถือเป็นโหมด 2 เสมอ (fail-safe)
5. **`hermes cron list` ซ่อนงานที่ paused** — ต้องดู `jobs.json` ตรงๆ หรือ `--all` ไม่งั้นจะเข้าใจผิดว่างานหาย
6. การเปลี่ยนโหมดมีผลกับ**รอบถัดไป**เท่านั้น (รอบที่กำลังรันอยู่ใช้ค่าเดิม) — ถ้าต้องการให้มีผลทันทีให้รัน `llm_rec_consumer_runner.py` เองหนึ่งครั้ง

## 6. แนวทางพัฒนาต่อ

- เพิ่มโหมดที่ 3: **"LLM ให้ความเห็นแต่มีสิทธิ์ยับยั้ง (veto) เท่านั้น"** โดยไม่ปรับน้ำหนัก
- ให้โหมด 2 กำหนด **น้ำหนักเสียง LLM ได้** (เช่น 30:70) แทนการตรึง 50:50 — เก็บเป็นคีย์ `llm_weight` ในไฟล์โหมด
- ทำ **หน้าจอสรุปโหมด** ในรายงาน Telegram รอบ 10 นาที (ตอนนี้แสดงในบรรทัด log ของ parser)
- ย้ายเมนูเลือกโหมดเป็น GUI (Tkinter/HTML) ถ้าผู้นำไปใช้ไม่ถนัด console
- บันทึกการเปลี่ยนโหมดลง audit (`mode_changed`) เพื่อตรวจย้อนหลังว่าระบบถูกใช้ในโหมดใดช่วงใด

## 7. ข้อจำกัดที่ต้องรู้

- สัญญาณภายในและสัญญาณ LLM ใช้ "คะแนนน้ำหนัก" จากฟอร์มตายตัว (`WEIGHT=0-100`) — คุณภาพจึงขึ้นกับวินัยในการกรอกฟอร์มของเสียงนั้น
- น้ำหนักที่เขียนลง config ถูก clamp ที่ `0.90–1.10` โดย engine เมื่อ `bounded_live` เปิด → ค่าที่แรงกว่านี้จะถูกตัดเงียบๆ
- การเลือกโหมดไม่กระทบ **การปรับ 36 ค่า + เกณฑ์ TP/SL** ที่ทำงานอัตโนมัติทั้งสองโหมด (คนละชั้นกัน: โหมด = "ใครมีสิทธิ์ออกเสียง", การปรับ = "ความยืดหยุ่นของเกณฑ์")
