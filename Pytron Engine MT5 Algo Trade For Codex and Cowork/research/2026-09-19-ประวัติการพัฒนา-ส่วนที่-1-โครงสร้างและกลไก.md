## 1) ระบบคืออะไร (ภาพรวม ณ สิ้นวัน)

ระบบเทรดทองคำ XAUUSD อัตโนมัติ ผ่าน MT5 (local bridge) แยกเป็น 3 ชั้นชัดเจน:

| ชั้น | หน้าที่ | ไฟล์หลัก |
|---|---|---|
| **เทรดคอร์** | ตัดสินใจ + ยิงออเดอร์ + จัดการไม้ — **ไม่พึ่ง LLM** (มี fallback) | `auto_trader.py`, `strategy_engine.py` |

**กลไกที่เพิ่ม/แก้ในวันนี้ (ใช้งานจริงแล้ว)**
- `side_net.py` — โมดูลกลางของประตู net (เดิมเขียนซ้ำ 2 ที่ในเทรดคอร์และเทรดเอนจิน)
- **ความถี่ขั้นต่ำบังคับใช้จริง** — อัตราไม้/วันนับเฉพาะเวลาระบบรัน+ตลาดเปิด ต่ำกว่า 2 → ผ่อนประตูหนึ่งขั้น (มีเพดานกันผ่อนเกิน)
- `market_clock.py` รู้จัก DST สหรัฐฯ — EDT เปิด 22:00 UTC / EST เปิด 23:00 UTC
- แผนที่ `position_id → strategy/side` — ทำให้วิเคราะห์กำไร/ขาดทุนรายกลยุทธ์ได้ครบ (เดิมเป็น unknown)
- `tools/rotate_audit.py` (หมุน/บีบอัด audit) · `tools/verify_market_hours.py` (ตรวจเวลาตลาดกับโบรกเกอร์)

**กติกา 3 ด่านของการตัดสินใจ**
1. **ด่าน 1 — ประตู net:** ผลไม้ย้อนหลังของ "กลยุทธ์+ทิศทาง" ติดลบ → ชะลอ; กลับเป็นบวก → เข้าได้ทันที (ดูเฉพาะไม้ที่ปิดภายใน **12 ชม.**)
2. **ด่าน 2 — 36 ค่า:** 12 กลยุทธ์ × 3 มิติ (raw / probability / weighted) ต้องอยู่ใน band ของตัวเอง
3. **ด่าน 3 — สองฝั่ง:** ผู้ชนะ = ผ่านด่าน 1+2 ฝั่ง pressure สูงสุด → เทียบฝั่งตรงข้ามด้วย 36 ค่า (ไม่ต้องผ่านประตู net) → ถ้าไม่มีตัวผ่านเลย = ไม่เทรด

## 2) ลำดับเหตุการณ์และการแก้ไขทั้งวัน (เรียงตามเวลา)

### 2.1 ต้นเหตุ "ไม่มีการเทรด" — band แคบผิดปกติ
- **อาการ:** ไม่มีไม้ใหม่หลายชั่วโมง · audit พบ 0 รอบที่มีตัวผ่านด่าน 2 ใน 40 นาที
- **วินิจฉัย:** ตัวปรับคำนวณ band ใหม่ **ทุก 1–3 นาที** และ weighted band แคบลงเหลือ **0.02** (เช่น `trend_buy` = [0.444, 0.464]) → ไม่มีคะแนนใดผ่านได้เลย
- **แก้:** เพิ่ม **ความกว้างขั้นต่ำมาตรฐาน** ทุกจุด (เจ้าของระบบกำหนด): **raw ≥ 0.10 · probability ≥ 0.10 · weighted ≥ 0.10** + บังคับในโค้ดเป็นขั้นสุดท้ายของตัวปรับ (ทุกเส้นทาง รวม mirror) + churn guard (คีย์เดิมปรับซ้ำ ≤1 ครั้ง/ชม.)

### 2.2 ประตูความน่าจะเป็นสูงกว่าค่าจริง
- **อาการ:** 114× raw / 114× weighted / 76× prob ถูกปฏิเสธใน 38 รอบล่าสุด
- **แก้:** ประตู prob = **p25 ของ 180 รอบล่าสุด** (เพดานการขยับ ±0.06/รอบ) + `window_records` 1000 → **180**
- **ผลประเมิน (รีเพลย์ 1,184 รอบจริง):** อัตราผ่าน **9.5% → 40.5% (4.2×)**

### 2.3 ไม้สวนแนวโน้ม (TP/SL) — ข้อมูลจริงหักล้างทฤษฎี
- เจ้าของระบบเสนอ: ไม้สวนแนวโน้มควร TP สั้นกว่า SL
- **จำลองด้วยราคา M1 จริง (107–116 ไม้):** TP<SL ให้ผล **แย่ลงทุกระดับ** (TP 1.4R = −0.170R · TP 0.5R = −0.467R)
- **มติ:** เลือก **"ข้อ ก"** = ยกพื้นคัดกรองไม้สวนแนวโน้ม **+0.05** (ยกได้ไม่เกิน 80% ของความกว้าง band → เหลือช่วง ≥0.02 เสมอ ไม่ตัน)
- **บทเรียน:** ทฤษฎีตลาดใช้ไม่ได้เสมอ — ต้องให้ข้อมูลจริงตัดสิน

### 2.4 "ไม่ทันพิธีเททอง" — ประตู net แช่แข็งคีย์จากไม้เก่า
- **วินิจฉัย (3 ชม. · 117 รอบ):** 60 รอบสัญญาณแรงผ่านด่าน 2 แต่ถูกประตู net สกัด (trend_sell ติด −0.81 จากไม้ที่ปิดนานแล้ว)
- **แก้:** ประตู net **กรองตามอายุไม้** (เจ้าของระบบเลือก **12 ชม.** จากตัวเลือก 6/12/24)
- **ผลประเมินจริง:** บล็อก 6 ชม. = 37.8% · 12 ชม. = 37.8% · 24 ชม. = 40.0% · ไม่จำกัด = 48.9%

### 2.5 ด่าน 3 (กติกาเจ้าของระบบ) — สองฝั่งด้วย 36 ค่า
- ผู้ชนะฝั่งซื้อ → เทียบกลยุทธ์เดียวกันฝั่งขาย → ถ้าฝั่งขายน่าสนใจกว่า **และผ่าน 36 ค่า** → เทรดฝั่งขายได้เลย (ไม่ต้องผ่านประตู net)
- ถ้าไม่ผ่าน → วนดู **กลยุทธ์ฝั่งตรงข้ามทั้งหมด** ด้วย 36 ค่า → เลือกตัวที่ดีที่สุด → ถ้า**ไม่มีตัวใดผ่านเลย = ไม่เทรด**
- **ผลจำลอง (600 รอบจริง):** keep 456 · พลิกฝั่ง 15 · ไม่มีตัวสำรอง 0 → จำลอง 15 ไม้ = win 60% · **+0.50R/ไม้**

### 2.6 ต้นเหตุ "ขาดทุนเร็ว" — ไม้ชนะเล็ก ไม้แพ้ใหญ่
- **วินิจฉัย:** ปิดกำไรตั้งไว้ **1/10 ของระยะ TP** → ไม้ชนะได้ $0.06–0.25 แต่ไม้แพ้ $0.40–0.53
- **ผลทดสอบ 3 ระดับ (ออเดอร์จริง 25 ไม้):** 50% → **−0.50R** ✗ · **80% → +5.80R** ✓ · 100% → +10.00R ✓
- **มติเจ้าของระบบ: 0.8** — จุดสมดุล (ได้กำไรชัด + ยังมีกลไกปิดก่อนกำหนดกันการกลับตัว)

### 2.7 กลไกใหม่ที่เจ้าของระบบกำหนด (19 ก.ย.)

**ก. Ticker ปิดไม้** — "ปิดไม้ทุกกรณี (SL/TP/cut-loss/ปิดกำไร) = จุดยิงเช็คเทรดใหม่ทันที"
ใช้ cadence เดิมของระบบ (ไม่เพิ่มรอบ) · บันทึก `close_ticker`

**ข. ระบบกันการแก้แค้น (Anti-Revenge)** — "ไม้ขาดทุนฝั่งไหน ห้ามเข้าฝั่งเดิมซ้ำภายใน 15 นาที เว้นแต่คะแนนแรงกว่าเดิม +0.05"
ลงโค้ด 4 จุด: จำข้อมูลไม้ที่เข้า → บันทึกตอนปิดขาดทุน → ตรวจก่อนยิงออเดอร์ → log `revenge_armed`

**ค. ระบบตัดขาดทุนใหม่ (early_cut)** — "ไม้เดิมกำลังขาดทุน + สัญญาณใหม่สวนทาง → ตัดทันที แล้วเช็คใหม่"
**ผลจำลอง 6 วัน (ไม้จริง 124 ไม้):** ไม้ขาดทุน 9 ไม้ ผลจริง **−$4.00 → ตัดเร็ว −$1.61 = ดีขึ้น +$2.39** ✓
ไม้กำไร 8 ไม้: ถ้าตัดเร็ว **−$1.93 แย่ลง** ✗ → **จึงใช้เฉพาะไม้ที่ขาดทุนเท่านั้น**

**ง. ไม้กำไร + สัญญาณสวนทาง → ปิดกำไร** — ตรวจแล้วมีอยู่แล้วในโค้ด (บรรทัด `opposite_signal`)

### 2.8 การแยกชั้น LLM + บอทดูแล LLM
- เจ้าของระบบ: "งานวิจัย 10 นาทีแบบ LLM ให้ใช้ระบบเหมือนแอดมินบอท — **ไม่ต่อ LLM ตรง** ให้บอทเป็นผู้ดูแล LLM เป็นสมองอีกชั้น"
- **เดิม:** สคริปต์ต่อ OpenRouter ตรง · **ใหม่:** `tools/llm_research_packet.py` เตรียมชุดข้อมูล (ไม่เรียก LLM) → บอทอ่าน → คิดด้วย LLM ของบอท → เขียนคำแนะนำ → consumer นำไปใช้
- **ทำงานร่วมกัน 2 แหล่ง:** ชุดข้อมูลบรรจุ `internal_research` (ผลวิจัยข้อมูลภายใน: auto_threshold_stats + รายงาน) + `recent` (audit) + `bot_loop` (คำแนะนำเดิมของบอท + ผลที่เกิดขึ้น)
- **ประตูโหมด** (`research_bot_gate.py`): โหมด 1 → งานบอทถูกข้าม (ไม่ใช้ LLM เลย) · โหมด 2 → บอทรันเต็มรูปแบบ
- **บทบาท 2 โหมด:** โหมด 1 = ระบบ Python สร้างคำแนะนำเองตามระบบเดิม · โหมด 2 = บอทเป็นสมองรวม 2 แหล่งและออกคำแนะนำเอง

### โมดูลกลาง: `outputs/mt5_python_bridge/news_feed.py`
เรียกฟังก์ชันเดียว = ได้งานวิจัยข่าวครบวงจร:
```
refresh()  →  ดึง RSS (investing.com 3 ฟีด) → ให้คะแนนผลกระทบต่อทอง → เก็บคลัง (dedupe)
              → วิเคราะห์ (ธีมมหภาค · ทิศทางสุทธิ · ระดับความระวัง)
              → เขียน research/news-log.md + research/news-research-<วันที่>.md
digest()   →  refresh() + ข้อความสั้นสำหรับป้อนบอท/แอดมินบอท
note()     →  refresh() + บันทึกวิจัยฉบับเต็ม
run_once() →  โหมด cron (บังคับดึงใหม่) + คืนรายการข่าวใหม่
```

**ออกแบบให้ง่าย ราบรื่น ประหยัดที่สุด**
- **คูลดาวน์ในตัว** `REFRESH_MINUTES = 5` — เรียกถี่แค่ไหนก็ได้ ดึงเน็ตจริงไม่ถี่กว่า 5 นาที (ครั้งอื่นอ่านคลังใน 0.001 วิ)
- **dedupe** ด้วยหัวข้อข่าว · เก็บคลังย้อนหลัง 48 ชม. · เขียนไฟล์แบบ atomic
- **วิเคราะห์ในตัว** — ไม่ใช่แค่ดึงข่าว: จัดธีม (ดอกเบี้ย/Fed · เงินเฟ้อ · ดอลลาร์ · พันธบัตร · ภูมิรัฐศาสตร์ · พลังงาน · มหภาค) + สรุปทิศทางสุทธิ + ระดับความระวัง

**โจทย์จากเจ้าของระบบ:** "บอทต้องรู้ทุกครั้งเมื่อสื่อสารกับ python script ต้องสื่อสารกันแบบไหน
บอทต้องรู้ครับ ต้องมีระบบทำให้บอทรู้ข้อนี้ครับ" (ทั้งโหมด 2 และแอดมินบอท)

**หลักฐานว่าจำเป็นจริง:** ไฟล์คำแนะนำที่บอทเขียนไว้ก่อนหน้า (11:51 · 12:16) **ไม่ผ่าน `validate()`**
ด้วยเหตุ `auto_apply != true` — คือบอทเขียนได้ แต่ระบบ **ดึงไปใช้ไม่ได้** → คำแนะนำตกหล่นเงียบ ๆ

### กลไกที่สร้างขึ้น (สัญญาสร้างจากโค้ดจริง ไม่เขียนมือ)

| องค์ประกอบ | หน้าที่ |
|---|---|
| `tools/rec_contract.py` | **สร้างสัญญาการสื่อสารจากโค้ดจริงของ consumer** → `research/recommendations/CONTRACT.md` (ถ้าโค้ดเปลี่ยน สัญญาเปลี่ยนตาม — ไม่มีทางหลุดจากความจริง) |
| `tools/submit_recommendation.py` | บอท **ตรวจคำแนะนำของตัวเองก่อนส่ง** (`--check` บอกชัดว่าผิดฟิลด์ไหน) + ส่งด้วยวิธีปลอดภัย (`--submit`) · เติม mode/epoch/เวลา ให้อัตโนมัติ |
| `tools/admin_command.py` | **คำสั่งที่แอดมินบอทสั่งระบบได้** (ไม่ใช่แค่คำแนะนำ) — `set_value` · `list_keys` · `admin_round` · `rollback_last` · `restore_factory` · `simulation` · `job` · `news_research` · `verify_market_hours` · ทุกคำสั่งตรวจกรอบ + บันทึก `work/admin_bot_log.jsonl` |
| `runtime_support.write_recommendation()` | กล่องจดหมายไฟล์เดียว: เขียน atomic + **สำรองของเดิมที่ยังไม่ถูกประมวลผลไว้ที่ `superseded/`** → ไม่มีคำแนะนำไหนหายเมื่อสองฝ่ายเขียนชนกัน |

### กติกาสำคัญ
- **ไฟล์เดียว:** `research/recommendations/latest_recommendation.json` — เจ้าของระบบกำหนดห้ามเปลี่ยนไปใช้ไฟล์อื่น (ไม่งั้นระบบข้อมูลภายในจะแตกเป็นสองทาง)
- **ฟิลด์บังคับ:** `schema` · `auto_apply=true` · `changes` ลิสต์ที่ไม่ว่าง · `mode`/`mode_epoch` ตรงกับระบบปัจจุบัน
- **ประตู 2 ชั้นกันคำแนะนำเก่าปน:** ตรวจโหมด + ตรวจ epoch

### เป้าหมายสูงสุดที่ฝังใน agent ทั้ง 2 ตัว (คำสั่งเจ้าของระบบ)
> "การทำกำไรสูงสุด ให้ได้เร็วและให้ได้มากที่สุด" — ทำทุกวิถีทางเพื่อให้บรรลุเป้าหมาย
> โดยใช้ตัวเลขจริงเป็นหลักฐาน · ตัดสิ่งที่ไม่ทำกำไร · เพิ่มน้ำหนักสิ่งที่ทำกำไร · ไม่หยุดนิ่ง
> **ภายในกรอบ:** ห้ามแตะคีย์สงวน · ห้ามสตาร์ท/หยุดตัวเทรด · ห้ามลบ kill switch · ห้ามแก้โครงสร้างโค้ด · ต้องคืนค่าโรงงานได้เสมอ

### ผลตรวจวงจรจริง (ทดสอบแล้ว)
บอทเขียน → `--check` (ไม่ผ่านเพราะขาด `auto_apply` → บอกเหตุผลชัด ✓) → แก้ → `--check` ผ่าน ✓
→ `--submit` ✓ → consumer อ่าน: `validate()` ผ่าน ✓ · ประตูโหมดตรง ✓ · ประตู epoch ตรง ✓
→ **สรุป: script python ดึงข้อมูลไปใช้ได้จริง ✓** (ทดสอบแล้วลบไฟล์ทดสอบออก ไม่ให้ถูก apply จริง)

## ภาคผนวก จ — ชั้น "สมอง" (Agentic AI) และระบบคำสั่ง (19 ก.ย. 2026)

**โจทย์จากเจ้าของระบบ:**
> "ตัว agent ทั้ง 2 ตัว คือบอทที่ทำงานหลัก — ถ้าใช้ Hermes ก็ Hermes เองเป็นบอทของทั้งสองชุด
> ในทำนองเดียวกันนี้ก็ต้องใช้ได้กับระบบ agentic AI ตัวอื่น ๆ ด้วย (OpenClaw · Manus · Codex ·
> Cowork · Claude Code · Cursor) และสำรวจสิ่งที่คล้ายกันในตลาดด้วย เราต้องทำระบบของเราให้เข้ากับทุกตัวได้"
> "ในระบบของ admin bot อาจจะไม่ใช่แค่คำแนะนำนะครับ อาจจะเป็นคำสั่งเลยจาก agent"

### สถาปัตยกรรม "ตัวถัง กับ สมอง"

| ชั้น | หน้าที่ | เปลี่ยนได้ไหม |
|---|---|---|
| **ตัวถัง** (`outputs/mt5_python_bridge/`) | ประตู 3 ด่าน · เครื่องยนต์เทรด · กรอบปลอดภัย · audit · โรงงาน | ❌ ห้ามแก้โครงสร้าง (เจ้าของระบบเท่านั้น) |
| **สมอง** (`agents/`) | วิเคราะห์ · วิจัยข่าว · เสนอคำแนะนำ · สั่งคำสั่งที่อนุญาต | ✅ เปลี่ยนได้ทุกเมื่อ ไม่ต้องแตะตัวถัง |

**สัญญากลาง:** ไฟล์ + คำสั่ง shell → agentic AI ตัวไหนทำได้ 2 อย่างนี้ ก็เป็นบอทของระบบได้ทันที
